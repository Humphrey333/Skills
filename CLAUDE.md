# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository state

This repo is a library of Claude Code **skills** (prompt/workflow documents), not software. There is nothing to build, lint, or test — no package manifest, no test suite, no CI. The artifacts are Markdown files; "correctness" means a skill triggers on the right requests, routes to the right sibling skill, and keeps its hard rules intact.

Tracked skills live in `<skill-name>/SKILL.md`, optionally with `references/*.md` for detail that would bloat the main flow (see `embed_debug/references/techniques.md`).

`andrej-karpathy-skills/` is a separate upstream clone, listed in `.gitignore` — reference material only. Don't edit or commit it.

`.gitignore` also covers `Requi*` (developer-supplied requirement notes, e.g. `embed_learning/Requirements.md`) and `Plans*` (this repo's own plan docs, e.g. `Plans/Plan_skills-library-readme_*.md`). Those files exist on disk but never show in `git status`. `README.md` and `LICENSE` at the root are tracked and describe the library for outside readers — update the README's catalog table and status list when a skill is added or its trigger changes.

## Activating a skill

Skills are **copied**, not symlinked, into `~/.claude/skills/`. Editing a file here does not change the skill Claude Code is running:

```bash
cp -r <skill-name> ~/.claude/skills/            # install or update
diff -r <skill-name> ~/.claude/skills/<skill-name>   # verify installed copy matches the repo
```

`AgentMD/install.sh` now does this for every skill (including `handoff`, `half-clone` and the new `embed_executing_plans`, `embed_programming`) and for the shared `AgentMD/AGENTS.md` / `CLAUDE.md` across Claude Code, Codex, Gemini CLI and Antigravity (`--link` symlinks instead of copying; overwritten items are replaced with no backup). `bash AgentMD/install.sh --gitea` also sets up the local Gitea review workspace (installs `tea` with brew, starts the `gitea` Docker container, guides the developer through their account, the `Agent` user, its token and collaborators, and runs `tea login add` for `Agent`); without the flag the script only warns. Test it with `bash AgentMD/tests/test_install.sh`; the target paths are one table at the top of the script. `AgentMD/ponytail/`, `AgentMD/superpowers/` and `AgentMD/humanize-writing-skill/` are git-ignored upstream clones, reference only — `embed_programming` and `embed_executing_plans` are forks of them (MIT, credited in each `SKILL.md`), and nothing upstream is installed.

Before the script existed, the installed set was: `embed_debug`, `embed_planning-embedded-topics`, `embed_summary`, `embed_create_coding_template`, `embed_document`, `embed_learning`. The installed `embed_create_coding_template`, `embed_document` and `embed_learning` also carry developer-supplied `Requirements*` files (git-ignored via `Requi*` in `.gitignore`), so `diff -r` will show those as "Only in" the installed side — expected, not drift. After copying, the session must be restarted for Claude Code to pick up the change.

## Skill roster and division of labor

The `embed_*` skills are a workflow chain for embedded Linux engineering (NVIDIA Jetson/L4T, Yocto, camera sensor bring-up — see the sibling project dirs under `/home/vito/Learning/Claude/`):

- `embed_planning-embedded-topics` — new topic (bring-up, subsystem, board support, feature): Research (facts + trade-offs, **no code**; documents read online with cited URLs, downloads listed in `Docs/REQUIRED_DOCS.md`; unanswered questions are asked again until answered or the developer says they can't find it) → Planning (developer picks direction, then a short plan: summary, recap of the decisions, `## Todo` checklist; no step-by-step section) → Hand-off to `embed_executing_plans`. After a clean recap and explicit final approval, saves `Plans/Plan_<topic-slug>_<YYYY-MM-DD>.md` **in the target project repo**, not here.
- `embed_debug` — existing bug/crash/misconfiguration: understand the code + info gate → one cause point per message (fixed Point template in short plain words, then wait for the developer) → solutions in words (Solution template, discussed with the developer) → after a recap and explicit yes, `Debug_<bug-slug>_<YYYY-MM-DD>.md` in the invocation directory. Hard rules: **no code or fix at all** (no patch, diff, debug print, script or invented value); ask, never assume; suspicious code unrelated to the reported symptom goes on an "also noticed" list offered at the end. Narrowing techniques (`references/techniques.md`) are checks the developer runs. Reasons from descriptions; does not run or reproduce on target hardware. Has its own `embed_debug/CLAUDE.md` — read it before editing there. Design record: `Plans/Plan_embed-debug-plain-explain_2026-10-13.md`.
- `embed_executing_plans` — runs after `embed_planning-embedded-topics` saves an approved plan: runs the plan's `## Todo` on `feature/<plan-slug>` or `fix/<plan-slug>` branched from an up-to-date `dev` (a project with no Gitea remote is stopped, since only new projects use this flow), one commit per todo, with no diffs in the CLI and no yes between todos. Before the first commit it runs `embed_programming_discussion`'s Agent check; after the last todo it hands the branch to `embed_programming_discussion` for the push, the pull request, the review and the merge. In bug-fix plans it records the developer's board results in `## Board results` and sends the loop back to `embed_debug` when no solution worked. Stops to ask when the plan is wrong. Loads `embed_programming` for code; at the end it only *proposes* `/embed_summary` and `/embed_document`. Forked from superpowers `executing-plans`. (`scripts/review.py`, the earlier local HTML review page, is no longer referenced.)
- `embed_programming` — loaded when code is written (every new or changed function gets a header comment: purpose, in/out, how it works, as Doxygen or kernel-doc; C/C++ also follows `references/cpp-embedded.md`: RAII and smart pointers, `constexpr` over `#define`, short interrupt paths, named sources): new code gets an extensible, manageable structure; existing code gets the smallest complete change (grep callers, reuse, no scope creep). Forked from ponytail without its levels or commands.
- `embed_programming_discussion` — the code review as a discussion in the developer's local Gitea (`http://localhost:3000`, `tea` 0.16, Gitea 28.2). Loaded by `embed_create_coding_template` (Step 2: `Agent` creates the private repo, pushes `main` + `dev`, transfers it to the developer, who keeps `Agent` as Write collaborator) and by `embed_executing_plans` (Step 1 Agent check; Step 3 push and `tea pulls create --base dev`; Step 4 read the review with `tea pulls review-comments` and the reviews API, fix, push, reply `tea pulls reply ... </dev/null` in one short line, record under `## Review results`; Step 5 confirm `merged: true`). Fixed defaults, never asked: developer user `Humphrey333`, Agent email `someAddress@gmail.com`, HTTP remote `http://localhost:3000/<owner>/<repo>.git` (no SSH). Always the Gitea user `Agent`: `tea --login Agent`, a repo-local credential helper pinned to it, repo-local git identity `Agent`; never the developer's token, never a merge, never `dev`/`main`. An unsubmitted review is a `PENDING` draft that `Agent` can't see. Does **not** load `embed_writing` (developer's choice, 2026-10-24). Design record: `Plans/Plan_embed-programming-discussion_2026-10-24.md`.
- `embed_summary` — manual `/embed_summary` only: harvests durable session knowledge into `~/.agents/Knowledge/<topic-slug>.md` + a one-line `INDEX.md` entry.
- `embed_create_coding_template` — runs after a plan is agreed in `embed_planning-embedded-topics`; copies `templates/project/` into `<plan repo root>/<project-name>/`, substitutes `@PLACEHOLDER@`s, specialises from the plan, then host-builds it, and finally (Step 7) loads `embed_programming_discussion` to create its Gitea repo (as `Agent`, transferred to the developer) with `main` and `dev`. Design record: `Plans/2026-10-10-embed-create-coding-template.md` (lives in the project repo the skill was designed in, not in this repo). Unlike the other skills it ships real files (`templates/`: CMake, lint configs, CI, shell scripts) — editing a template means re-copying the whole skill dir. `grep -rn '@[A-Z_]*@'` on a generated project must stay empty, so a new placeholder must be added to `templates/README.md` too.
- `embed_document` — manual `/embed_document` only: creates or updates a project's `README.md` and `BUILD.md` from evidence (its `Plans/`, code/build files, `git log`), CLI-focused + TOC style (awesome-readme). Runs in the invocation directory; BUILD.md is host build only; only functions listed in Plans are documented, with each one's working status asked of the developer. Shows a diff and waits for yes before writing; unknowns are asked or become `TODO:` markers. Section rules live in `references/readme-structure.md`. Design record: `Plans/Plan_embed-document-readme-build_2026-10-11.md` (also not in this repo). Has its own `embed_document/CLAUDE.md` with skill-specific rules — read it before editing there (`embed_planning-embedded-topics/CLAUDE.md` likewise). Complements `embed_create_coding_template` (first-draft docs) — this one keeps them true afterwards.
- `embed_learning` — auto-triggers on learning requests: Claude acts as a 20-year professor teaching the developer foundations → best practices applied to embedded work (learner profile is hardcoded in `SKILL.md` by the developer's choice). F1 builds a 7-day × 1-hour learning path (base→medium, advanced only if asked): asks first for the local Markdown ebook folder, then recommends ≤5 books per level that are not in it (named from expertise, checked by an online search with cited URLs, any format, free ones tagged); F2 is a book companion working only from supplied material, every claim and example cited; F3: path days are examined by a per-topic `learn.py` (copied from `templates/learn.py`; stdlib Python, serves `templates/exam.html` on 127.0.0.1, grades multiple choice against `.learn/bank_day<N>.json`, logs `.learn/attempts.jsonl`, rebuilds the `Progress.md` table, releases `.learn/notes/day<N>.md` into `Notes/` on a pass). At path approval Claude writes the whole kit for every day at once (24-question bank + note per day; `learn.py` refuses a bank whose right option is the longest in over 40% of questions, so distractors match its length, and at least half of medium and traps carry a `code` snippet; plus a learner `README.md` from `templates/topic-README.md` that explains every file and lists the week's days); Claude never records a path-day result. Book-chapter and review exams keep the paste flow (`Exam_<source>.html` + `_key.md`, graded by Claude). **Day gate: a day is passed only at 100%; retakes are unlimited and draw the least-shown questions.** Output lives in the topic folder the developer confirms, registered in `~/.agents/Learning/INDEX.md`. Formats: `references/bank-format.md`, `references/notes-format.md`, `references/exam-format.md`; placeholders `@TOPIC_SLUG@`, `@TOPIC_TITLE@` in `templates/README.md`. Like `embed_create_coding_template` it ships real files, so editing a template means re-copying the skill; tests: `python3 -m unittest discover -s embed_learning/tests`. Design records: `Plans/Plan_embed-learning-skill_2026-10-11.md`, `Plans/Plan_embed-learning-exam-runner_2026-10-18.md`.
- `embed_writing` — loaded by every skill whose output a person reads (`embed_debug`, `embed_planning-embedded-topics`, `embed_document`, `embed_learning`, `embed_summary`, `embed_create_coding_template`, `embed_executing_plans`, `handoff`; not `half-clone` or `embed_programming`). Edits wording only, **reword, never remove**: replaces AI-writing signs (`references/ai-signs.md`: Wikipedia "Signs of AI writing" + humanize-writing) with plain words of the same meaning, strips only chatbot leftovers and tool markers, and keeps every fact, reason, hedge, warning and list item (a meaning check in Step 5). Commands, numbers, quotes, `TODO:` markers, feature status, headings, template text and required questions pass through untouched. Doubtful or unsourced sentences are kept and flagged to the caller, never deleted; the strict sourcing rule for README/BUILD.md lives in `embed_document`. Returns the clean text plus one `changed: …; stripped: …; flagged: …` line for the developer. Forked from humanize-writing (MIT) with its LinkedIn rules and "not for docs" exclusion dropped. Design records: `Plans/Plan_embed-writing-skill_2026-10-17.md`, `Plans/Plan_embed-writing-keep-meaning_2026-10-18.md`. Each caller carries one "Writing pass" line and a Common Mistakes bullet; keep both when editing a caller.
- `handoff` / `half-clone` — session continuity pair, both manual. `handoff` writes a curated `HANDOFF.md` (Goal / Done So Far / What Worked / What Didn't Work / Next Steps); `half-clone` writes `HALF-CLONE.md`, a trimmed transcript of the recent half of a conversation with bulky tool output collapsed. Each skill's `When to Use` explicitly points at the other for the wrong case.

Each skill's `description` and `When to Use` must carry that negative routing ("Not for: X — use Y instead"); it is what keeps the skills from stealing each other's triggers.

## The shared-knowledge layer

`~/.agents/Knowledge/` is the cross-project memory that ties the chain together: `embed_summary` writes it (reading it first to pick the slug and dedupe), and `embed_planning-embedded-topics` reads it as **Step 0 — Load Shared Knowledge** before doing anything else. No other skill reads it. Slugs are global across projects, so they must be specific (`imx586-mipi-csi-bringup`, not `camera`).

Only `embed_planning-embedded-topics` carries the Step 0 block. Do not add it to other skills. Its semantics: read `INDEX.md`, open every matching topic file, tell the developer in one line what loaded (or that nothing matched), and when a knowledge entry conflicts with what the developer says now, the developer wins and the conflict gets flagged for `/embed_summary`.

## Conventions for writing or editing a skill

**Executing a plan here** (developer's choice, 2026-10-24): edit the skill files in the working tree only, running every todo without a yes per step. Create no branch, commit or push in this repo; the developer does git by hand. Local tests are fine. The Gitea flow of `embed_executing_plans` is for new projects, not for this repo. The plan itself still needs approval.

Structure every `SKILL.md` the way the existing ones are structured — deviation makes the set harder to maintain:

1. YAML frontmatter with `name` (matching the directory name exactly) and a `description` that is **always double-quoted** (`description: "Use when …"`, inner `"` escaped as `\"`), because an unquoted description containing `: ` is invalid YAML and GitHub will not parse it. The description starts "Use when …", names concrete triggers, and ends with the negative routing case.
2. `# Title` → `## Overview` (core principle in a few lines) → `## When to Use` (positive bullets + a `Not for:` bullet) → numbered Stages or Steps (`## Step 0` only in `embed_planning-embedded-topics`) → `## Common Mistakes`.
3. `## Common Mistakes` is a mirror of the rules above it — every hard rule and skipped-step failure in the body gets a corresponding bullet. Keep them in sync when adding a rule.
4. Harden a rule that Claude will be tempted to rationalize past with a `| Rationalization | Reality |` table (see `embed_planning-embedded-topics` Stage 1).

Recurring hard rules — preserve these when editing, and carry them into new skills:

- **Read online, never download** (developer's choice, 2026-10-23, "prefer online" 2026-10-24). Every skill prefers reading documents online: it searches and reads without asking, and must cite the URL of every fact it takes from one. No skill downloads a file (datasheet, TRM, errata, app note, book, archive); downloads are done by the developer by hand. Only a document that can't be read online goes into `Docs/REQUIRED_DOCS.md` in the project folder (`<topic-dir>/Docs/` for `embed_learning`), one row per document: Document, Revision, Why needed, Search terms, Status (`needed`, then `supplied: Docs/<file>` or `not found (developer)`); then the skill waits for the developer to supply it. `Docs/` is local only (`.git/info/exclude`).
- **Re-ask until answered.** In planning and debug, a question the developer didn't answer, or answered with something that doesn't settle it, is asked again; it is skipped only when the developer says they can't find it or have no information.
- **Code review happens in Gitea** (new projects only, 2026-10-24), always through `embed_programming_discussion` as the Gitea user `Agent`. `embed_create_coding_template` and `embed_executing_plans` hold no `tea` commands of their own. The one-time setup is in `AgentMD/README.md` ("Gitea setup (once)"); `install.sh` warns when `tea` or the `Agent` login is missing.
- **Ask, never assume.** A stated assumption ("I'll assume X unless told otherwise") does not satisfy this; an inference from the codebase is a *suggested answer* inside a question, never a confirmed one.
- **Propose, then wait.** Anything that writes to the developer's knowledge files or picks a direction requires explicit confirmation first.
- **Manual-only skills must not self-trigger** (`embed_summary`, `handoff`, `half-clone`).
- Prose is addressed to Claude-as-executor and refers to the user as "the developer."
- **Output a person reads goes through `embed_writing`.** When adding a skill, or giving an existing one new human-read output, ask the developer whether it should load `embed_writing`; if yes, add a "Writing pass" line at the step that shows or writes the text, and a Common Mistakes bullet. Exceptions by the developer's choice: `embed_programming_discussion` (pull request text and one-line replies stay raw), plus `half-clone` and `embed_programming`.
